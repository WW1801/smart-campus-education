## 第三章 详细设计

### 3.1 界面设计

#### 3.1.1 典型使用流程

**流程一：教师录入成绩**

```
教师登录 → 成绩管理 → 成绩录入
  → 选择学期+课程 → 系统加载学生列表
  → 行内输入平时成绩/考试成绩
  → 系统按权重自动计算总成绩
  → 点击"批量保存" → 状态=pending
  → 管理员审核通过 → 状态=approved
```

**流程二：学生选课**

```
学生登录 → 选课管理
  → 输入学号+学期 → 点击"查询可选课程"
  → 系统展示课程列表（含先修/冲突/容量标记）
  → 点击"选课" → 确认弹窗 → 系统校验6层规则
  → 选课成功 → 课表自动更新
```

**流程三：排课冲突检测**

```
教务管理员 → 排课管理 → 课程安排
  → 点击"新增排课" → 填写排课信息
  → 点击"检测冲突" → 系统返回冲突列表
  → P0冲突(教师时间) → 保存按钮禁用
  → P2/P3冲突 → 警告提示，允许保存
  → 无冲突 → 保存成功
```

#### 3.1.2 关键界面说明

| 页面 | 核心交互 | 设计要点 |
|------|---------|---------|
| 成绩录入 | 行内编辑+权重展示 | 根据课程性质自动显示权重比例（必修30%+70%等） |
| 选课页面 | 状态标记+容量指示 | 已选/先修未通过/时间冲突三重Tag，余量颜色区分 |
| 排课安排 | 冲突检测弹窗 | ConflictTip组件按P0-P3优先级分色展示 |
| 课表查询 | CSS Grid网格 | 行=节次，列=星期，课程卡片含课程名/教师/教室 |
| 学籍变更 | 动态可选状态 | 根据当前状态计算可流转目标状态 |

#### 3.2.3 关键设计决策

**1. course_schedule 三时间索引（违背范式但合理）**

为支持排课冲突的O(1)级查询，在 course_schedule 表上建立三个复合索引：
- `idx_teacher_time(semester_id, teacher_id, day_of_week, start_period, end_period)`
- `idx_classroom_time(semester_id, classroom_id, day_of_week, start_period, end_period)`
- `idx_class_time(semester_id, class_id, day_of_week, start_period, end_period)`

理由：排课冲突检测是高频操作，三个索引分别覆盖教师/教室/班级三个冲突维度，避免全表扫描。索引冗余在可接受范围内。

**2. student_course_selection 的 UNIQUE 约束**

`uk_student_schedule(student_id, schedule_id)` 防止学生对同一排课重复选课，在数据库层面保证数据一致性，优于应用层校验。

**3. teaching_plan.prerequisite_ids 使用 VARCHAR 而非关联表**

先修课程ID以逗号分隔存储（如 "CO001,CO002"），而非建立独立的先修关系表。理由：先修课程数量极少（通常1-2门），VARCHAR+应用层解析的方案更简洁，避免多一次JOIN查询。

### 3.3 关键算法

#### 3.3.1 排课冲突检测算法

```
输入：待排课记录 schedule(semester_id, teacher_id, classroom_id,
                        class_id, day_of_week, start_period, end_period)
输出：冲突列表 conflicts[]

1. 查询同一学期 + 同一天的所有已有排课记录 sameTimeSchedules
2. FOR EACH existing IN sameTimeSchedules:
   a. 时间重叠判定: existing.start_period ≤ schedule.end_period
                    AND schedule.start_period ≤ existing.end_period
   b. IF 重叠:
      - IF existing.teacher_id == schedule.teacher_id:
          → 冲突P0(教师时间冲突, 不可违反)
      - IF existing.classroom_id == schedule.classroom_id:
          → 冲突P2(教室时间冲突, 可换教室)
      - IF schedule.class_id != NULL
        AND existing.class_id == schedule.class_id:
          → 冲突P3(班级时间冲突, 可调时段)
3. RETURN conflicts

保存策略: P0冲突 → 拒绝保存; P1/P2/P3 → 警告但允许保存
```

**时间复杂度**：O(n)，n为同天排课记录数，通过复合索引优化，实际n很小。

#### 3.3.2 选课6层校验算法

```
输入：student_id, schedule_id, semester_id
输出：选课成功 / 抛出BusinessException

校验1: 重复选课 → 查询selection表是否已存在(student_id, schedule_id)
校验2: 选课时间窗口 → 查询semester.status是否为current
校验3: 先修课程 → 查询teaching_plan.prerequisite_ids
       → 逐个检查grade表是否有approved且total_score≥60
校验4: 时间冲突 → 查询已选课程的day_of_week+period是否重叠
校验5: 选课模式 → class_based模式不允许自由选课
校验6: 选课容量(乐观锁) →
       freshSchedule = SELECT * FROM course_schedule WHERE schedule_id=?
       IF freshSchedule.current_students >= freshSchedule.max_students → 拒绝
       UPDATE course_schedule SET current_students = current_students + 1
         WHERE schedule_id = ? AND current_students < max_students
       IF affected_rows == 0 → 并发冲突，拒绝
```

**乐观锁设计**：校验6使用 `UPDATE ... WHERE current_students < max_students` 的CAS模式，避免超卖。无需加分布式锁，单条SQL保证原子性。

#### 3.3.3 成绩权重计算算法

```
输入：usual_score, exam_score, course_nature
输出：total_score

IF exam_score IS NULL:  // 缺考
    RETURN 0

SWITCH course_nature:
    CASE 'compulsory':       // 必修课
        total = usual × 0.30 + exam × 0.70
    CASE 'elective_major':   // 专业选修
        total = usual × 0.40 + exam × 0.60
    CASE 'elective_public':  // 公共选修
        total = usual × 0.50 + exam × 0.50

RETURN ROUND(total, 2)

绩点计算:
    IF total >= 60: gpa = (total - 50) / 10
    ELSE: gpa = 0
    GPA = Σ(单科绩点 × 学分) / Σ学分
```

#### 3.3.4 学籍状态流转算法

```
合法流转表:
    active    → {suspended, graduated, dropped}
    suspended → {active, dropped}

禁止流转:
    graduated → 任何状态 (终态不可逆)
    dropped   → active (需重新注册)

退学劝退条件: 累计不及格学分 ≥ 20 (可配置)
```
